Use music_status first. If unconfigured, follow SETUP.md shipped with the app; never borrow another owner's token, library, or tunnel. music_home, music_search and music_account_library are read-only MCP tools. Use music_account_library with kind status/playlists/likes/playlist and a playlist id for playlist tracks; signed-out account library connects through /wizard-youtube-music/. Account library is bounded to 100 items, separate from Wizard taste, and does not imply playback entitlement or preferences sync. Browser playback is a user-gesture action in the Music view, not an MCP promise. Library scan and feedback use the documented API; use only owner-authorized files. Never claim native background playback from the web package.

## Identify a song
- In Music, tap Identify (or say exactly `music`, `shazam`, `what's this song`, `identify this`). This starts a 30-second shared capture with music processing left off. Stop and identify seals early. A saved clip survives recognition failure, offline upload and navigation.
- Hunts shows saved captures and unsolved audio. Open a hunt to replay the original or normalized recording, compare a candidate preview, play its full song through Music, mark This is it / Not it, add a candidate manually, retry, share/export, or inspect attempts. This is it likes the resolved Music track and counts as an explicit request; Download to library reuses Music's cached full song.
- MCP: `identify_list` and `identify_get {id}` are read-only. `identify_retry {id}` starts recognition of existing saved audio. `identify_confirm {candidate_id}` is a write: only after the owner says that candidate is right. Confirmation is idempotent and survives a hub restart.
- Discard on a finished no-match reversibly hides it from Identifications immediately; Undo restores the same capture after durable API readback. Recording, uploading, pending and matched captures cannot be discarded. Audio, attempts and candidates stay intact. Navigating away does not lose the Undo/error action; failures restore the list entry and offer retry. Never discard an owner capture merely to test this action.
- MCP writes `identify_discard {id}` and `identify_restore {id}` require the owner's intent; both are idempotent. `identify_list` excludes discarded captures, while `identify_get` still reads them. Retry requires restore first.
- HTTP: POST `/wizard-music/api/identify/captures/{UUID}/discard` or `/restore`, JSON `{}`. Returns 200 plus the stored capture, 400 for malformed UUID, 404 for a missing record, 409 for an ineligible/busy capture. GET by UUID verifies `retention_state: discarded|active`; the ordinary capture list excludes discarded records even after restart.
- HTTP: `/wizard-music/api/identify/captures`, `/captures/{UUID}`, `/captures/{UUID}/audio?kind=original|normalized|export`, POST `/captures/{UUID}/retry`, POST `/captures/{UUID}/candidates`, POST `/candidates/{integer}/verdict` with `verdict: confirmed|rejected`, `/search?q=...`, `/retention/dry-run`. Capture POST accepts raw audio with a stable UUID `?id=...`, saves/fsyncs first, rejects a different digest at the same UUID and never re-enqueues an identical retry. Acknowledge shared capture only after GET returns the expected raw_sha256.
- Default provider: shazamio (unofficial; no signup), ffmpeg-normalized overlapping windows plus a filtered fallback. AudD and ACRCloud are off, no paid calls. A no-match is an honest outcome, not an excuse to discard audio. No retention operation deletes audio automatically.
- The hub's `hub/import_trackhunt.py SOURCE_DIR HUB_HOME --backup BACKUP_DIR` uses SQLite online backups, copies and hashes audio, maps candidate IDs and refuses conflicting capture IDs. Keep legacy data for at least 30 days after cutover.

## Playlists and long mixes
- Home → Playlists → Add link saves a YouTube playlist or long-mix video. A video does not need `list=`. Name is optional; without supplied metadata the label honestly shows the resource ID. No network metadata lookup, playback, media download, song splitting, remote import or YouTube account write happens on Save.
- MCP `playlist_list {}` reads the same list; `playlist_save {url,title?,author?,authorUrl?,thumbnail?}` saves only with the owner's intent. Preserve the supplied URL exactly and the full known title. Accept only HTTPS YouTube video/playlist links. Read `playlist_list` after saving and verify exact URL/title/id before claiming success. Equivalent URLs deduplicate by the underlying video/playlist ID; the first exact URL and metadata win.
- HTTP GET/POST `/wizard-music/api/playlists` uses the same object; GET returns `{playlists:[...]}`, POST the saved record. Hub SQLite stores it in additive `saved_playlists`, distinct from playback-history `/api/mixes`.
- Tapping a row plays it inside Music; Music never sends the owner to YouTube (wizard-os#654). A long mix plays as one track; a YouTube playlist plays its songs in order as a Music queue, read on that tap through the YouTube Music connector (public playlists need no signed-in account; a private one needs the connected account). `POST /wizard-music/api/playlists/<id>/play` returns `{track, tracks}`. Provider playback can fail: Music shows a plain error with Retry. Do not promise streaming merely because a link was saved, and never offer a youtube.com link as a fallback. Saving never imports a playlist's tracks.

## Your own playlists
- When the owner asks for a playlist ("fetch a bunch of music and make me a playlist"): run `music_search` a few times, pick track ids (`yt:*` / `lib:*`), then `playlist_create {name, track_ids}` once. Only on the owner's request. The answer is the playlist read back from Music plus `skipped` ids; report the real count and name, never more than was stored.
- `playlist_add_tracks {id, track_ids, position?}`, `playlist_remove_tracks {id, track_ids}`, `playlist_update {id, name?, description?, track_ids?}` (track_ids sets the whole order) and `playlist_get {id}`; `playlist_list` shows them as `songPlaylists`. The owner plays it from Home → Your playlists → Play.

## More like this stations
- When the owner says they love a song's sound and want more like it ("I love Trap by Gui Boratto, play me more like it"): call `station_curate {track_id | query, note}` once, with their own words about what they like in `note`. The answer is the station read back from Music: `title` ("Like Trap · Gui Boratto"), `profile` (the sound in one line), the first 10 `tracks` and `open` (the link that plays it in Music). Report those real tracks and give the owner the `open` link; `picks: radio` means no AI connection answered and it is plain radio with Music's station rules.

## Phone music apps (Navidrome)
- The owner's own music files play from Navidrome, bundled with Music, and any Subsonic phone app (Symfonium, Substreamer, play:Sub, Amperfy) can play the library and Music's playlists over the tailnet. Your tools work the same. When the owner asks how to connect a phone app, send him to Music → Sources → Phone music apps: the server address is shown there, and any user name and password works because the tailnet signs him in. Never invent an address or a password.
